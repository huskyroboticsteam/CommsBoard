# CommsBoard

Firmware for the Husky Robotics Communication Board: it records every CAN packet on the
rover bus to a microSD card as timestamped JSON Lines. It runs on an STM32G474RET6 and is
being built first on a Nucleo-G474RE dev board.

The design is described in *Comms Board Firmware Architecture v2*. This repository
implements chapters 0 to 5 of that document.

## How it works

```
CAN bus -> FDCAN2 interrupt -> RX ring -> can_task -> log ring -> logger -> microSD
           (timestamps)        512 rec               3072 rec    (JSON lines)
```

There is no RTOS. `main()` runs one loop forever, and each pass runs three jobs in turn:

- **`can_task_poll`** moves records from the RX ring into the log ring and sends queued
  frames. It never waits: if the log ring is full, records are dropped and counted.
- **`logger_poll`** is the only code that touches the card. It turns records into JSON
  lines, packs whole lines into 512-byte blocks, and writes them. It has two staging
  buffers: while one is being written, records that arrive are formatted into the other.
- **`status_poll`** blinks the heartbeat LED, prints a stats line every 5 s on the debug
  UART, and feeds the watchdog only while the loop is still making progress.

The **interrupt** timestamps each frame, copies it into a ring buffer as a 16-byte
record, and returns. It never waits.

A card write can take a long time. Whenever the SD driver has to wait on the card, it
calls `app_yield()`, which runs the CAN and status jobs. So a slow write does not stall
CAN handling, even without an RTOS.

The architecture document is written around FreeRTOS and names a main loop as its
fallback. This firmware uses the fallback.

Log files are `/LOG/B<boot ID>_<part>.jsonl`. Each file is preallocated when it is
opened, so writing data never changes the FAT, and a power cut can only damage the block
being written.

## Layout

| Folder | Contents |
|---|---|
| `App/board` | `board.h`: the pin map and interrupt priorities; LEDs |
| `App/drivers` | `can_drv`, `sd_spi`, `timebase`, `dbg_uart` |
| `App/services` | `ringbuf`, `logrec`, `jsonl`, `fmt`, `timekeeping`, `storage` (no hardware in the first five) |
| `App/app` | `can_task`, `logger`, `status`, and the main loop in `app_main` |
| `App/config` | `config.h`: every tunable number |
| `Core`, `Drivers`, `Middlewares`, `FATFS` | Generated by STM32CubeMX from `CommunicationBoard.ioc` |
| `tests` | PC tests |
| `tools` | `logread.py`, `gen_version.sh` |
| `docs` | [Log file format](docs/log-format.md), [pin map](docs/pin-map.md) |

In CubeMX-generated files, our code lives only inside `USER CODE BEGIN/END` blocks, as
one-line calls into `App/`. Regenerating from the `.ioc` keeps it.

## Build and flash

Open the project in STM32CubeIDE, build the **Debug** configuration, and run it on the
Nucleo. Debug output is on the ST-LINK virtual COM port at 115200 baud.

The build is for the Nucleo unless the compiler is given `-DBOARD_COMMS_V1`. On the
Nucleo, CAN runs in **internal loopback** (no transceiver needed), and the log header
says `"loopback":true`. In loopback every frame the board sends also comes back as a
received frame.

## Tests

```
make -C tests
```

This runs on a PC (gcc or clang, plus Python 3):

- **`test_services`**: unit tests for the ring buffer, record packing, JSON formatter and
  time maths.
- **`test_logger`**: the real logger, storage, SD driver and FatFs code against a
  simulated SD card, through five boots (normal, boot ID, file rollover, card fault,
  card full).
- **`check_logs.py`**: parses every line the tests wrote with Python's `json` module and
  with `logread.py`.

## Reading a log

```
python3 tools/logread.py B00042_01.jsonl
python3 tools/logread.py B00042_01.jsonl --csv frames.csv
```

It prints a summary (boot, line counts by kind, frame rate, frames dropped) and says
where the valid data ends. The rest of a preallocated file is unused space.

The full format (blocks, header, every kind of line, and how to find where the valid
data ends) is in [docs/log-format.md](docs/log-format.md).
